# Byter roadmap

**Идея:** «А что, если бы Limine был на телефонах?» Byter должен давать
понятный и повторяемый способ загрузить собственное AArch64-ядро на телефоне,
сохраняя привычную модель запросов Limine. Первая целевая платформа — Nothing
Phone (3a), код платформы и загрузчика живёт в `Boot/`, а `example/` показывает
использование ABI.

Сейчас работает экспериментальная цепочка `fastboot boot → ARM64 shim → ELF`;
пример ядра запрашивает framebuffer и рисует квадрат. Это подтверждает путь
до ELF и часть Limine request ABI, но пока **не означает совместимость с Limine
Boot Protocol**. В частности, протокол по умолчанию считает ядро запрашивающим
base revision 0, а текущий handoff не выполняет её требования к отображению
памяти и состоянию ARM64.

## Этапы

### 1. Надёжная платформа A059

**Статус:** в работе. Shim уже читает геометрию и формат framebuffer из DTB
`simple-framebuffer`; если ABL его опускает, использует изолированный профиль
A059. Проверка DTB-пути на телефоне ещё не выполнена.

- Получать адрес, разрешение и формат framebuffer из DTB/реального интерфейса
  дисплея телефона. Для известных вариантов ABL держать проверенный fallback в
  отдельном A059-профиле, а не размазывать константы по общему коду.
- Собирать точную карту RAM и reserved regions из DTB, явно резервировать shim,
  загруженное ELF, DTB, стек и данные handoff.
- Добавить надёжную диагностику загрузки: этап, причина отказа и состояние CPU
  при входе от ABL, без изменения изображения framebuffer загрузчиком.
- Зафиксировать поддерживаемый путь запуска: только RAM через `fastboot boot`,
  пока не появится отдельная необходимость в другом носителе.

**Готово, когда:** пример запускается на A059 через данные DTB либо отдельный
fallback-профиль, а ошибки загрузки можно различить без угадывания по циклу
перезагрузок.

Для A059 опубликован DTS с framebuffer-узлом в `/chosen`, свойствами `reg`,
`width`, `height`, `stride` и `format`. Это ориентир для парсера, но конкретный
DTB, передаваемый ABL на устройстве, ещё нужно проверить отдельно. [Патч DTS
Nothing Phone (3a)](https://www.spinics.net/lists/kernel/msg6114343.html)

### 2. Корректная основа Limine ABI

**Статус:** в работе. Shim уже отвечает на memory-map request: карта содержит
RAM из DTB и известные резервации, включая shim, DTB, PT_LOAD-сегменты ядра и
framebuffer. Проверка ответа независимым ядром и на A059 ещё предстоит; это не
полная карта всех физических областей и не заявление о совместимости с Limine.

- Сделать сканирование запросов соответствующим официальным маркерам начала и
  конца; проверить границы каждого объекта и версию конкретного запроса.
- Реализовать корректные ответы для bootloader info, DTB, framebuffer и
  memory map; для неподдерживаемого запроса оставлять `response == NULL`.
- Добавить HHDM и executable address только вместе с реальными отображениями и
  адресами, которые они описывают.
- Вести таблицу: запрос, поддерживаемая revision, обязательные поля, источник
  данных и ограничения Byter.

**Готово, когда:** независимое ядро, использующее `Boot/include/byter.h`, может
запросить эти структуры и получить согласованные данные, а не значения-заглушки.

### 3. Загрузка ELF как у Limine

- Перейти от текущего требования `p_paddr == p_vaddr` к отдельным физическим и
  виртуальным адресам `PT_LOAD`.
- Поддержать требуемый higher-half адрес ядра и точные права сегментов ELF;
  сохранить проверки размеров, выравнивания, переполнения, пересечений и точки
  входа.
- Возвращать физическую и виртуальную базу загруженного образа через стандартный
  executable address response.
- Зафиксировать начальный формат поддержки (AArch64 ELF64 `ET_EXEC`); PIE,
  релокации и дополнительные форматы добавлять отдельными согласованными этапами.

**Готово, когда:** минимальное ядро с раздельными VMA/PADDR загружается по своим
виртуальным адресам и видит корректные права `PT_LOAD`.

### 4. ARM64 handoff и выбранная base revision

- Подготовить 4 KiB translation tables для ядра, HHDM и обязательных областей;
  назначить корректный memory type framebuffer и обычной RAM.
- Передать управление с согласованными `TTBR`, `TCR`, `MAIR`, `SCTLR`, стеком,
  масками прерываний и уровнем исключений.
- Сопоставить каждый пункт реализации с одной выбранной base revision Limine.
  До выполнения всех требований не объявлять эту revision поддерживаемой.
- Добавить в `example/` проверку base revision и выводить квадрат только после
  успешной проверки контракта.

**Готово, когда:** ядро использует переданные page tables и HHDM, проверяет
подтверждённую base revision и проходит документированный ARM64 handoff без
зависимости от случайного состояния ABL.

### 5. Привычный workflow Limine

- Добавить конфигурацию загрузки с простым форматом, понятными сообщениями об
  ошибках, параметрами ядра и выбором записи.
- Сначала упаковывать конфигурацию, ядро и модули в RAM-образ, который уже
  передаётся через `fastboot boot`; не начинать с реализации UFS-драйвера.
- Реализовать стандартные module и command-line requests только после появления
  понятного формата и времени жизни загруженных файлов.
- Сохранить короткий путь для новичка: изменить `example/` или выбрать своё ELF,
  выполнить одну команду сборки и загрузки.

**Готово, когда:** пользователь может собрать образ с конфигурацией, ядром и
модулями без редактирования shim и вручную заданных адресов.

### 6. Расширение платформ

- Отделить общую загрузку ELF и Limine ABI от A059-специфичных входа, DTB,
  дисплея и Android boot image.
- Добавлять следующий телефон только после фиксации его ABL-контракта и
  воспроизводимого теста загрузки.

## Не входит в ближайшие этапы

- Прошивка разделов телефона: текущий безопасный цикл разработки остаётся
  RAM-only через Fastboot.
- Полноценная ОС и драйверы телефона: `example/` остаётся небольшим примером
  протокола, а не местом для развития ядра Byter.
- UEFI `.efi`-загрузка: основной целевой формат этого проекта — Limine ABI для
  AArch64 ELF; иной путь потребует отдельного решения по платформенной модели.

## Протокольный ориентир

Развитие сверяется с [официальной спецификацией Limine Boot Protocol](https://github.com/Limine-Bootloader/limine-protocol/blob/trunk/PROTOCOL.md)
и [официальным `limine.h`](https://github.com/Limine-Bootloader/limine-protocol/blob/trunk/include/limine.h).
Спецификация определяет base revisions, раскладку памяти, HHDM и состояние
ARM64 при передаче управления; совпадения request ID и структур недостаточно
для заявления полной совместимости.
