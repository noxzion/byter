# Byter roadmap

**Идея:** «А что, если бы Limine был на телефонах?» Byter должен давать
понятный и повторяемый способ загрузить собственное AArch64-ядро на телефоне,
сохраняя привычную модель запросов Limine. Первая целевая платформа — Nothing
Phone (3a); код загрузчика живёт в `Boot/`, а независимый проект
[`byter-template`](https://github.com/noxzion/byter-template) показывает
использование ABI.

Сейчас работает экспериментальная цепочка `fastboot boot → ARM64 shim → ELF`;
тестовое ядро запрашивает framebuffer и рисует квадрат. Это подтверждает путь
до ELF и часть Limine request ABI, но пока **не означает совместимость с Limine
Boot Protocol**. Shim обрабатывает Byter base-revision-0 tag, но карта памяти
пока строится только по RAM и известным reservations из DTB. ARM64 handoff
настраивает свои таблицы страниц и переводит выполнение на EL1.

## Этапы

### 1. Надёжная платформа A059

**Статус:** A059 fallback проверен на Nothing Phone (3a). Тестовый запуск без
fallback показал, что в переданном ABL DTB нет узла `/chosen/framebuffer*`;
экран берётся из отдельного A059 fallback-профиля. RAM, `/reserved-memory` и
FDT memory reservation block разбираются, а их области за пределами RAM теперь
включаются в упорядоченную карту. Вариант карты до этого изменения проверен на
устройстве; новую обработку внешних reservations ещё нужно подтвердить на A059.

- Получать адрес, разрешение и формат framebuffer из DTB/реального интерфейса
  дисплея телефона. Для известных вариантов ABL держать проверенный fallback в
  отдельном A059-профиле, а не размазывать константы по общему коду.
- Проверено на устройстве: FDT reservations включены в карту; shim, ELF, DTB,
  стек и данные handoff резервируются отдельно. Новую обработку reservations вне
  RAM нужно проверить на устройстве.
- Shim выводит этапы и ошибки текстом через framebuffer-консоль со шрифтом
  8×16; ранний отказ до определения framebuffer пока не виден на экране.
- Зафиксировать поддерживаемый путь запуска: только RAM через `fastboot boot`,
  пока не появится отдельная необходимость в другом носителе.

**Готово, когда:** тестовое ядро запускается на A059 через данные DTB либо отдельный
fallback-профиль, а ошибки загрузки можно различить без угадывания по циклу
перезагрузок.

Для A059 опубликован DTS с framebuffer-узлом в `/chosen`, свойствами `reg`,
`width`, `height`, `stride` и `format`. Это ориентир для парсера, но конкретный
DTB, передаваемый ABL на устройстве, ещё нужно проверить отдельно. [Патч DTS
Nothing Phone (3a)](https://www.spinics.net/lists/kernel/msg6114343.html)

### 2. Корректная основа Limine ABI

**Статус:** базовые ответы проверены на Nothing Phone (3a). Тестовое ядро подтвердило
base revision, карту памяти, executable mapping и framebuffer через HHDM; зелёный
финальный квадрат появляется после всех этих проверок. Карта содержит RAM из DTB
и известные резервации, включая shim, DTB, PT_LOAD-сегменты ядра и framebuffer.
Shim также учитывает request delimiters и оставляет `response == NULL` для
неизвестных запросов и неподдерживаемых ревизий. Это всё ещё не полная карта
физических областей и не заявление о совместимости с Limine.

- Сделать сканирование запросов соответствующим официальным маркерам начала и
  конца; проверять границы общего заголовка и ревизию каждого запроса.
- Реализовать корректные ответы для bootloader info, DTB, framebuffer и
  memory map; для неподдерживаемого запроса оставлять `response == NULL`.
- Проверено на устройстве: HHDM pointers на responses, framebuffer и memory-map
  entries доступны ядру после включения таблиц страниц.
- Проверить, что executable address и раздельные VMA/PADDR остаются согласованы
  с отображениями после расширения набора ABI-указателей.
- Таблица запросов, ревизий, источников данных и ограничений ведётся в
  [`Boot/ABI.md`](Boot/ABI.md); обновлять её вместе с реализацией.

**Готово, когда:** независимое ядро, использующее `Boot/include/byter.h`, может
запросить эти структуры и получить согласованные данные, а не значения-заглушки.

### 3. Загрузка ELF как у Limine

**Статус:** проверено на Nothing Phone (3a): ядро с раздельными VMA/PADDR
загружается и продолжает работу после включения MMU.
Shim загружает AArch64 ELF64 `ET_EXEC` по `p_paddr`, отображает каждый
`PT_LOAD` по `p_vaddr` и применяет права сегмента. Пример связан в higher half;
его executable address response содержит отдельные физическую и виртуальную
базы.

- Проверено на устройстве примером: HHDM mapping, указатели ABI и framebuffer
  доступны после включения MMU.
- Сверить оставшиеся требования выбранного Byter handoff revision 0.
- PIE, релокации и дополнительные форматы добавлять отдельными согласованными
  этапами.

**Готово, когда:** минимальное ядро с раздельными VMA/PADDR загружается по своим
виртуальным адресам и видит корректные права `PT_LOAD` на устройстве.

### 4. ARM64 handoff и выбранная base revision

**Статус:** Byter handoff revision 0 и переход в ядро проверены на устройстве:
тестовое ядро принимает base-revision tag и использует переданные HHDM и memory map.
На A059 тестовое ядро нашло в переданном ABL DTB переводимый device `reg` и подтвердило,
что диапазон целиком отмечен `RESERVED` в memory map: центральный квадрат зелёный,
голубой диагностический маркер виден в левом верхнем углу. Образ с отображением
известных reservations выше 4 GiB в identity map и HHDM дошёл до зелёного demo
на A059. Диагностический пример проверяет identity/HHDM-трансляцию такого `reg`,
если он есть. Последний запуск завершился зелёным с голубым маркером:
подходящего внешнего device `reg` выше 4 GiB в runtime DTB A059 не найдено.
Неоднозначные и непереводимые диапазоны пропускаются; полной
совместимости с Limine base revision 0 пока нет.

- На Nothing Phone (3a) ядро достигло EL1 и прошло проверки base-revision tag,
  HHDM и memory map. Тестовое ядро также выполнило EL1 SVC, проверило exception class в
  `ESR_EL1` и успешно вернулся через `eret`. IRQ, FIQ, SError и abort recovery
  пока не проверялись и остаются фатальными.
- В тестовом ядре проверять хотя бы один DTB `reg`-ресурс, целиком
  отмеченного `RESERVED`: голубой маркер подтверждает её, красный означает отказ.
- Сверить оставшиеся требования Limine base revision 0; не объявлять полную
  совместимость до закрытия ограничений карты памяти и handoff.
- Тестовое ядро ищет внешний `reg` выше 4 GiB, проверяет покрытие `RESERVED` и
  проверяет аппаратной трансляцией identity map и HHDM для начала, середины и
  конца диапазона. Пурпурный маркер означает, что такой диапазон найден и прошёл;
  голубой — что подходящего диапазона в runtime DTB нет.
- Сохранять цветовой статус последнего пройденного этапа при остановке.

**Готово, когда:** ядро использует переданные page tables и HHDM, проверяет
подтверждённую base revision и проходит документированный ARM64 handoff без
зависимости от случайного состояния ABL.

### 5. Привычный workflow Limine

- Конфиг читается при сборке. Повторяющиеся `entry=`, `kernel=` и `cmdline=`
  задают до 16 пунктов; упаковщик помещает каталог и все ELF в RAM-образ.
  Старый формат с `kernel=`/`cmdline=` остаётся совместимым.
- Runtime menu показывает пользовательские названия: Volume Up/Down выбирают
  пункт, Power запускает его, таймаут выбирает первую запись. Essential Key
  запрашивает перезагрузку в bootloader Fastboot. Меню центрировано над логотипом
  Nothing и не стирает splash screen. Выбор нескольких разных ELF и возврат в
  Fastboot нужно подтвердить на устройстве.
- Ранее тестовое ядро сравнило полученную строку с `byter.example=1`; зелёный
  квадрат подтвердил cmdline и проверки handoff. Сборку ядра и образа теперь
  выполняет отдельный template.
- Минимальный независимый template опубликован в
  [`noxzion/byter-template`](https://github.com/noxzion/byter-template); общие
  ABI, shim и утилиты хранятся в его ветке `assets`.
- Следующий шаг: добавить модули к entry-каталогу и реализовать module request,
  сохраняя передачу RAM-образа через `fastboot boot`.
- Реализовать стандартные module и command-line requests только после появления
  понятного формата и времени жизни загруженных файлов.
- Сохранить короткий путь для новичка: изменить template или выбрать своё ELF,
  выполнить одну команду сборки и загрузки в репозитории template.

**Готово, когда:** пользователь может собрать образ с конфигурацией, ядром и
модулями без редактирования shim и вручную заданных адресов.

### 6. Расширение платформ

- Отделить общую загрузку ELF и Limine ABI от A059-специфичных входа, DTB,
  дисплея и Android boot image.
- Добавлять следующий телефон только после фиксации его ABL-контракта и
  воспроизводимого теста загрузки.

## Не входит в ближайшие этапы

- Прошивка разделов телефона: текущий безопасный цикл разработки остаётся
  RAM-only через Fastboot.
- Полноценная ОС и драйверы телефона: развитие ядра относится к отдельному
  проекту template, а не к репозиторию загрузчика.
- UEFI `.efi`-загрузка: основной целевой формат этого проекта — Limine ABI для
  AArch64 ELF; иной путь потребует отдельного решения по платформенной модели.

## Протокольный ориентир

Развитие сверяется с [официальной спецификацией Limine Boot Protocol](https://github.com/Limine-Bootloader/limine-protocol/blob/trunk/PROTOCOL.md)
и [официальным `limine.h`](https://github.com/Limine-Bootloader/limine-protocol/blob/trunk/include/limine.h).
Спецификация определяет base revisions, раскладку памяти, HHDM и состояние
ARM64 при передаче управления; совпадения request ID и структур недостаточно
для заявления полной совместимости.
